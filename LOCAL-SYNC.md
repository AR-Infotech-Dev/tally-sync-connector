# Company-wise local sync — Connector 0.1.17

Company identity v2 separates branches sharing a native GUID. Discovery reads CompanyNumber and DataPath/DirectoryName; a private key combines GUID with the locator when available, otherwise GUID plus normalized company name. Server and Connector use the same versioned key algorithm. Public API company_id remains the Server's per-client sequence. SQLite schema 8 keeps each branch's masters, vouchers, opening bills, published components and checkpoints under its private key. Existing GUID-only caches are retained but inactive and need a new sync, because the old implementation could overwrite one branch with another. Name-based identities require deliberate relinking after rename; data-folder moves/renumbering also require relinking. See COMPANY-ROUTING.md for registry migration details.

Sync completes selected master categories before starting accounting preparation: Company details, Ledger masters, then Stock item masters. Raw masters are staged first, re-read and verified, and published to independent master components before opening summaries or voucher indexes are requested. If opening bills or transactions fail, those verified masters remain available for Dealer Code / Item Code lookups and appear in category readiness; the resumable session and saved voucher chunks remain. Publishing masters keeps stock staging intact for the later full snapshot. Accounting reports continue using the previous complete snapshot until opening data and vouchers pass final verification. Masters-only runs finish after master verification.

Opening bill summaries now accept unreferenced On Account allocations, normalize native Agst Ref adjustments, and accept valid compact or ISO bill dates. Zero-amount placeholder bill rows do not prevent sync. On Account funds have a separate internal grouping/storage key from a real named bill, even when the bill is literally named On Account. Non-zero named bills still require a reference and an in-range valid calendar date; failures now identify the ledger, reference, type, raw date and requested range. Existing saved chunks can be resumed after updating the Connector; clearing app data is unnecessary.

The Sync screen has inclusive From Date and To Date inputs, defaulting to the current Indian financial year (1 April–31 March). On 3 November 2026 the defaults are 2026-04-01 to 2027-03-31. Voucher indexing, details and verification use these dates; masters remain independent of the period. Automatic sync also defaults to the current financial year. The Tally screen period is not inherited. The period is part of the checkpoint identity, so different periods cannot reuse each other's sessions. Resume restores the saved dates. Legacy checkpoints without dates remain visible but are not reused as dated sessions.

Each completed voucher sync replaces the company's published report snapshot with the selected period; it does not accumulate separate report periods. Readiness shows the published dates. Statement, group summary and outstanding requests outside cached dates return an error. Opening ledger balances and older pending bills are now prepared automatically for the selected start date. Existing dated caches need one successful voucher sync on this version; deleting SQLite or syncing all historical voucher details is unnecessary.

Opening preparation reads original ledger balances and opening bill allocations in batches of at most 100 ledgers. Tally then aggregates pre-period ledger movements and bill adjustments into calendar-month summaries ending the day before From Date. Only these summaries cross the network, not old voucher details or inventory. Date filters are explicit. Cancelled, optional, order and other non-posting voucher types (including custom descendants) are excluded from summary totals. Slow or oversized summary windows split down to a day with a timeout cooldown. Successful summary chunks are stored under OpeningHistory in the existing checkpoint store; they are freshly revalidated on resume rather than blindly reused after possible backdated changes. Normal master counts exclude those summary records.

The opening baseline is verified again before publication. SQLite schema 7 stores pending opening bills in cache_opening_bills by dataset, ledger and reference. Opening ledger balances, pending bills and selected-period vouchers publish atomically; failed or interrupted sync preserves the previous snapshot. Outstanding combines the baseline with in-period bill adjustments, nets matching references and omits settled bills for Pending Bills. A ₹10,000 opening bill and ₹3,000 receipt therefore produce ₹7,000 pending without double-counting the old invoice. Baseline failure is surfaced with its phase rather than publishing incomplete balances.

Voucher indexes and historical summary collections apply an explicit `$Date >= ##SVFromDate AND $Date <= ##SVToDate` filter: static date variables alone did not restrict native Voucher collections and could repeat the same vouchers in each monthly window. Detail requests use exact IDs from that validated manifest; deep native subcollection fetches can change Tally's date-variable context, so returned dates are checked again in the parser. Manifest responses are checked against the requested dates, and repeated MasterIDs across ranges stop indexing before progress can be inflated. Existing saved chunks and the previous complete snapshot remain preserved on failure.

Voucher indexing now starts with calendar-month windows through the current month, plus a future-date tail so post-dated vouchers are retained. A slow or oversized range splits into smaller ranges, with a cooldown after timeouts. Split plans persist in `cache_sync_range_plans`, preventing the same broad timeout from being repeated after restart. Single-day indexes can fall back to bounded MasterID reads; if even that index fails, sync stops with its exact phase and preserves prior chunks. Connectivity and malformed-response failures are not retried as range-size failures. The UI shows the current range and IDs found separately from saved voucher details.

Connect the Connector to Server, open the required company in the configured Tally instance, then open **Sync** in the sidebar. Refresh companies and select one. This selects only the local sync target; API Push/Fetch still uses the request's client-scoped company_id and Server GUID mapping.

Select Company details, Ledger masters, Stock item masters, or Vouchers. Company identity/details are always included. Voucher sync automatically includes ledger and stock item masters so a complete accounting snapshot has consistent dependencies. Parent groups and Dealer Codes are included with ledgers; Part Numbers / Item Codes are included with stock items. Separate Group, Unit or Godown master catalogs are not added by this change.

Choose 25, 50 or 100 vouchers per chunk and a 250–5000 ms delay (defaults: 100 / 500 ms). Ledger and stock master details are also read in chunks of at most 100 after a lightweight MasterID/AlterID index. Oversized responses reduce chunk size automatically. Use **Pause sync** to stop, and **Resume** beside a saved checkpoint or **Start / resume selected sync** with the same categories to continue. Only one local sync worker runs at a time. Open a closed company in Tally and refresh before resuming it.

Automatic incremental sync is **off by default**, including installations without this preference. Settings > Background Service > Automatic sync checks current-period records for open companies every three minutes and reuses saved opening history. It never prepares missing opening history automatically. A manual selection does not restrict API access to other companies. Pausing stops the current schedule until a new sync or connection/settings change starts it again.

SQLite keeps:

- `cache_sync_sessions`: scope/company/category plan, persistent stage identity, state and progress settings.
- `cache_sync_master_rows`: validated master chunks with MasterID, AlterID signature and normalized details.
- Existing staging voucher/entry tables: committed voucher chunks, keyed by company session and MasterID/signature.
- `cache_components`: publication timestamps and datasets for independently ready masters and full accounting data.

Restart no longer deletes staging rows belonging to a resumable session. Resume re-reads current master/voucher indexes, fetches changed/missing records and drops deleted/outdated staged versions. Master changes invalidate staged vouchers conservatively. Batches commit atomically; retries do not duplicate vouchers or allocations. Keep the local SQLite database to retain checkpoints. Disconnecting or pausing preserves them. Legacy orphan staging from versions without sessions is cleaned up; already discarded chunks from an older version cannot be recovered.

Successful complete voucher sync verifies its source again and atomically publishes the full company snapshot. Failures leave the previous published snapshot untouched. Masters-only sync publishes separate master datasets for Dealer Code / Item Code lookups and shows **Selected masters saved**; it does not make accounting reports ready or replace an existing complete report snapshot. Readiness shows each category's count and publication time.

The local database upgrades in place to schema version 7. This change does not delete Tally files, repair TSTATE.TSF, change network shares, or guarantee elimination of Error 53. The client PC's Tally data path/access problem still needs verification. Tests cover an interrupted 9,960-voucher run after 3,000 committed records, SQLite reopen/resume, changed/deleted vouchers, master chunk reuse, pause, scoped selection, and partial report readiness. That fixture is not a live 9,960-voucher client test.

Run `npm run build` for the renderer. Installed clients need a newly packaged 0.1.12 installer; building the UI alone does not update them.


## Saved opening history
Verified opening balances and pending bills are stored in cache_opening_baselines by server/client/Tally scope, company identity and From Date. Normal sync reuses them, including after restart or a later voucher failure. Automatic sync never creates or rebuilds a missing/invalid baseline; run manual Sync once. Change Refresh opening history after pre-period vouchers/bill allocations change or company restore. Historical changes are not automatically detected: reports reflect the last prepared baseline until manual refresh. Changes to ledger names, identity, Books From, or original opening amounts invalidate reuse. Date-range end changes alone do not invalidate the baseline. Failed refresh preserves the previous published report snapshot. Initial/explicit preparation is still verified twice and may be expensive; this change removes repeated historical work from subsequent automatic syncs, not Tally data-path errors.


## Live Movement Analysis size limits
Movement PDFs read live Tally data independently of local voucher sync. Exports now use explicit date and MasterID filters, select only inventory fields required by the report, and read calendar-month ranges sequentially. Oversized responses split dates down to a day, then split disjoint MasterID ranges. Chunk totals are combined before computing weighted rates. Out-of-range/duplicate IDs and failed chunks reject the entire report. A single-day timeout stops without repeated ID scans. The 5 MiB transport cap is unchanged. This needs the updated Connector; native client Tally verification remains required.


## Reinstall and uninstall
Normal uninstall keeps Electron userData (ledger-cache.sqlite, checkpoints, settings and logs). The interactive uninstaller asks whether to permanently remove this Windows user's saved data; No is the default. Updates and silent uninstallations preserve it. Select Yes only for a complete reset. This does not touch Tally company files. Reinstall as the same Windows user and use the same Server URL, Client ID and Tally URL/port to reuse the same cache scope. Manually deleting AppData removes the cache; changed company identity or incompatible historical cache migrations can still require a fresh sync. The prompt applies only to newly built uninstallers, not an already installed older version.
